Option B · Semantic capsules, built to spec

macOS Designer, 24 September 2026. This is the chosen direction, drawn at the medium PanelScale (480pt wide, 20pt control height, 16pt glyph box, 13pt glyph, 5pt off-state radius, 14pt row gap, 7pt inside the mic group). SF Symbols cannot be loaded in a browser, so every glyph is a hand-drawn SVG approximation. Judge colour, fill and rhythm, not glyph shape. No Swift has been changed.

Assumption I made and am flagging, not hiding

The mirror toggle is green (#3AD862), the same as video. Reasoning: mirror acts on the camera preview, so it belongs to the same semantic family as the S/M/L preview-size toggles, which you assigned green for exactly that reason; giving it its own fourth hue would add a colour that means nothing new. The one argument against, which you should weigh: mirror and video then look identical while idle even though one records and the other only reframes, and the only thing separating them is the glyph.

Second, smaller assumption: the camera menu's chevron well is green too, since the menu picks the camera. It is accent-blue today.

These ratios are identical in light and dark mode, because the glyph sits on the capsule fill, not on the panel. What does change with appearance is the capsule's own edge against the panel: green on the light popover is 1.74:1 and green on the dark popover is 7.42:1, so on a light panel the green capsules have a weak boundary. In the off state the 1pt separatorColor outline supplies that boundary; in the on state Option B removes it.

Plainly: which ones fail

  • Every green capsule fails. That is five of the nine controls: video, mirror, and all three S/M/L toggles. 1.88:1 against a 3:1 requirement is not marginal, it is roughly half.
  • Both embers fail across the bright half of their cycle, green worse than red. A glyph that is legible at one moment and washed out two seconds later is a worse failure than a constant one, because it reads as a rendering bug.
  • Red and blue capsules pass, with no margin to spare on red (3.57).

What fixes it, without giving up the scheme

Three ways, in order of how little they disturb the chosen design. This is a report, not a decision.

  • Black glyph on green only. Keeps your exact hex. Costs consistency: the row would then have white glyphs on red and blue and black glyphs on green, which undercuts "one control family".
  • Darken the green to #10913A. Keeps the white glyph and the family rule, at 4.09:1. It is no longer the FaceTime green you were pointing at.
  • Accept the failure and document it. Defensible only if you decide the glyph is decorative and the capsule itself carries the meaning. It is not decorative here: the glyph is the only thing separating mirror from video, since both are the same green.

Colourblind: red beside green

Under deuteranopia and protanopia, #FF383C and #3AD862 converge toward the same muddy yellow-brown, and in this scheme the mic and video capsules are two controls apart inside the same tight group. Three non-hue channels survive that:

  • The glyph. mic.fill versus video.fill are unmistakably different shapes, and this is the channel doing all the real work.
  • The amber corner dot. It already exists, it already suppresses under Reduce Motion, and it sits on whichever medium is live, so it answers "which one is recording" without hue.
  • Ember rhythm, if you want it to. Both embers currently run at 3.4s. Giving video a different period would make medium legible from motion alone. I have deliberately not done that: two controls drifting at unequal rates in the same row looks broken far more often than it looks informative, and only one medium can ever be live at a time, so the two rhythms are never seen together. Available if you want it; not recommended.

Net: audio versus video is distinguishable without colour. What is not distinguishable without colour is mirror versus video versus S/M/L as a family, since they share one hue by design; that grouping falls back entirely on position and glyph, which is how the row reads today anyway.

Capsule geometry: what the off state looks like now

This is the part of Option B with the largest implementation consequence, so it is stated exactly.

Height & glyph boxidentical, 20pt tall, 16pt glyph box, 13pt glyph at medium. Only the horizontal padding grows 4pt → 6pt so the capsule ends clear the glyph.

Does the row still read as one control family? Honestly: partly. Off, all nine controls are the same 5pt rounded rect with the same outline, so the resting row is a clean family. On, a control changes both its silhouette and its edge treatment at once, so an on control is not "the same control filled" but a different shape. The pin, at the far left, is the clearest case: idle it is a rounded square, pinned it is a pill.

Two things keep it from breaking apart, and both are load-bearing, so do not let them drift in implementation:

  • Height never changes. All nine controls hold the same 20pt cap height at every state, so the row keeps one horizontal baseline and one rhythm no matter how many capsules are lit.
  • Padding change is 2pt and symmetric. The control gets marginally wider when on. At medium that is invisible; at the small scale it comes out of the camera menu's width, which is already the only flexible item in the row and was widened to 380pt for the mirror toggle. Check that arithmetic before implementing.

Known trade-offs

Stated once, for the record, then dropped. The direction is settled.

  • The white-glyph contrast failure on green is the one item here that is a defect rather than a preference, and it affects five of nine controls. It needs a decision before implementation, not after.
  • Accent colour is no longer honoured inside the row. A user who set a graphite or pink accent still gets a red/green/blue panel.
  • Increase Contrast now needs hand-tuned variants per hue rather than one derived value, because none of these colours are semantic.
  • The corner-radius change between off and on is a real discontinuity, mitigated but not removed by the constant cap height.
