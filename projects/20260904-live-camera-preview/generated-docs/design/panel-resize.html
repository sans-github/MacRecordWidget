Panel resize — 200pt to 504pt

The video toggle now has two effects: it still arms Photo Booth for the next Start, and it now opens the preview. The panel grows from 200×31pt to 504×346pt.

Read the two panels as one panel at two moments. The right edge never moves; the left edge travels 304pt out to the left. The button row is trailing-aligned inside the content column, so its four controls sit at the same screen coordinates in both frames — the user’s pointer does not have to chase them.

What moves and what does not

  • The button row keeps its fixed 200pt frame and is trailing-aligned in the content column, so the four controls do not resize, reorder, reflow or translate (AC-PNL-5). Trailing alignment is what makes them stay visually still; a frame with no explicit alignment centres the row and it would slide 152pt left as the panel grows.
  • The preview and the control strip appear below the row. Growth is downward and leftward: the trailing edge is pinned, so the extra width appears on the leading side. Nothing is inserted above the row, ever (AC-PV-1).
  • Turning the toggle off removes the preview and the strip from the layout entirely — not hidden, not zero-height (AC-PV-3) — and the panel returns to exactly the shipped 200pt geometry.
  • The capture session is tied to this same toggle: it starts on toggle-on while the panel is open, stops on toggle-off and on panel close, and resumes on reopen (AC-LC-1 to AC-LC-4).

Anchoring — resolved

The trailing edge is the fixed edge. The panel is anchored on its right; the button row is anchored on its right; everything that grows, grows to the left and downward. This replaces the open question raised in the first draft of this page.

If the status item is not near the right edge, mirror the whole thing. The rule is: the row is anchored to whichever edge the window is anchored to. A status item near the left of the menu bar clamps the other way — the panel’s leading edge pins and it grows rightward — and the row must then be leading-aligned to stay still. A status item with room on both sides re-centres, and no static alignment holds the row still; centre alignment is the least-bad choice there because the row then moves half as far. The app ships one status item in one place, so implement the trailing case and leave the alignment as a single named constant rather than a literal, so flipping it is a one-line change if the anchoring ever proves different on a real machine.

A horizontal shift of the row would be a positional change, not a reflow, so a centred row would not strictly violate AC-PNL-5. It is still wrong: the four controls are the panel’s only permanent affordances and they should not move under the pointer when the preview opens.

Animation

UnverifiedThe 200→504pt growth may not animate at all

The design below specifies an animated width change gated on accessibilityReduceMotion. That is the intent, and it is what should be built first. But withAnimation animates SwiftUI layout inside the hosting view; the containing NSWindow frame for a MenuBarExtra(.window) panel is typically resized in one step. The likely outcome is that the window snaps to 504pt while the content animates inside it, which reads as a flash or a clip rather than smooth growth. Nobody has observed this yet — it is a prediction from how AppKit hosts SwiftUI content, not a measurement, and it is not presented as fact.

Smallest experiment that settles it. A throwaway app: one MenuBarExtra(.window) whose content is a coloured rectangle with .frame(width: expanded ? 504 : 200, alignment: .trailing), toggled inside withAnimation(.easeInOut(duration: 0.22)). Screen-record the toggle twice: once with the status item near the right edge of the menu bar (this app’s case, and the case the anchoring spec above assumes) and once with it mid-bar. Two recordings answer both open items at once — whether the window animates or snaps, and which edge it pins. Half a day at most, and it must be run by a human on a real Mac.

If it snaps: do not fight it with a custom NSWindow animation. Drop the width animation to a snap in both Reduce Motion states, keep the trailing anchor (which matters more — it is what keeps the controls still), and raise it to EM as a design change rather than absorbing it silently.

Implementation constraint — there is no native preview control

SwiftUI has no camera preview view on macOS 14. The preview surface must be an NSViewRepresentable wrapping an NSView whose layer is an AVCaptureVideoPreviewLayer, fed by an AVCaptureSession the app owns and manages. This is a required AppKit interop, not a shortcut, and it carries obligations the rest of this app has never had:

  • NSCameraUsageDescription in the Info.plist — the string is user-visible in the system prompt, so it is copy and belongs in the message table on the states page, not in an engineer’s judgement.
  • The camera entitlement (com.apple.security.device.camera) in the sandbox entitlements file.
  • A first-run permission prompt the app has never shown before — the shipped app needs no Accessibility permission and asks for nothing. The denied and not-yet-granted states are specified on the states page; they are reachable states, not edge cases.
  • Mirroring is set on the capture connection (isVideoMirrored), not with a SwiftUI .scaleEffect(x: -1) — scaling the hosted layer fights the layer’s own geometry.
  • Session lifecycle is the app’s to run: start on toggle-on, stop on toggle-off and on panel close, resume on reopen (AC-LC-1 to AC-LC-4). Nothing about this is automatic.

This does not change the design. It is recorded here so the cost is visible at the mock stage rather than discovered mid-implementation.
